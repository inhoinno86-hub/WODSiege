# SQLite·증빙 영상 오프라인 백업/복구

현재 단일 `state(id=1, data JSON)` SQLite와 `uploads/` 전용 도구다. Node.js 22.13 이상에서 추가 의존성 없이 실행한다. 계정·Box·경기·원장·포인트와 영상 파일을 보존하며 **복구 시 모든 로그인 세션을 무효화**한다. 원본 DB와 원본 백업의 세션은 변경하지 않는다. 보관/삭제 정책이나 자동 백업 스케줄러는 포함하지 않는다.

## 실행 전 조건

- API와 업로드/데이터를 변경하는 모든 프로세스를 종료하고 자동 재시작도 중지한다. 백업부터 검증 완료까지, 복구부터 전환까지 정지 상태를 유지한다.
- 실제 쓰기에는 `--execute --server-stopped`가 모두 필요하다. 이 플래그는 운영자의 정지 확인이다. **현재 서버와 공유하는 잠금이 없어 도구가 정지 상태를 강제하거나 증명할 수 없다.** 실행 중인 서버의 DB와 영상이 함께 일관된 시점에 저장된다고 보장하지 않는다.
- 대상은 부모 디렉터리가 이미 있는 **새로운 디렉터리**여야 한다. 기존 대상, 원본 내부/상위 대상, 경로의 `..`, 경로 구성요소의 심볼릭 링크, 루트/홈/현재 작업 디렉터리를 거부한다. 파일은 하드 링크·심볼릭 링크·디렉터리·장치 파일을 거부한다.
- 경로와 부모는 신뢰할 수 있는 운영자만 변경할 수 있어야 한다. 적대적 사용자가 작업 도중 부모 경로를 바꾸는 환경에 대한 완전한 경합 방어 도구가 아니다. 원본+백업+복구본을 담을 충분한 공간이 필요하다.
- 백업에는 비밀번호 해시·세션 해시·사용자 식별정보·위치·비공개 영상이 들어 있다. 새 디렉터리는 `0700`, 파일은 `0600`으로 만든다. 암호화·원격 전송·보존 기한·키 관리는 제공하지 않는다. 접근 제한된 암호화 저장소를 별도로 사용하고 Git/공개 공유 폴더에 넣지 않는다.

## 백업

아래 `backups` 부모 폴더는 운영자가 접근 제한된 로컬 위치에 미리 준비한다. 날짜 경로는 매번 새 이름을 사용한다. `--source`는 실제 `WODSIEGE_DATA_DIR`를 명시한다. 도구가 환경 변수에서 자동으로 원본을 고르지 않는다.

```bash
# 읽기/검사만 수행하는 기본 모드. 대상 디렉터리를 만들지 않는다.
node scripts/data-backup.mjs backup --source ./data --target ./backups/2026-09-06-01

# 모든 데이터 작성 프로세스가 정지했음을 운영자가 확인한 뒤 실행
node scripts/data-backup.mjs backup --source ./data --target ./backups/2026-09-06-01 --execute --server-stopped

node scripts/data-backup.mjs verify --source ./backups/2026-09-06-01
```

SQLite를 읽기 전용으로 열고 `VACUUM INTO`로 별도의 독립 DB를 만든다. 원본 DB 파일만 단순 복사하는 방식과 달리 SQLite가 읽는 **커밋된 WAL 내용도 포함**한다. 원본 체크포인트나 SQL 변경은 실행하지 않는다. SQLite 읽기 연결 자체가 엔진의 WAL 공유 메모리/잠금 파일을 사용하거나 생성할 수 있으므로 원본 디렉터리의 바이트 단위 무변경까지 보장하지는 않는다. 검증·dry-run에도 이 SQLite 읽기 동작이 적용된다.

`uploads/`의 모든 일반 파일을 복사한다. DB에서 참조하지 않는 파일도 보존하며 자동 삭제하지 않는다. 현재 서버의 UUID 형태와 호환되는 영문/숫자/하이픈/밑줄 파일명만 허용한다. DB의 영상 ID, 제출 기록의 영상 참조, 참조 파일의 크기를 확인한다. 백업 전후 JSON 차이와 복사 중 파일 변화도 검사하지만, 이 검사는 서버 정지 조건을 대체하지 않는다.

생성 구조:

```text
2026-09-06-01/
  manifest.json          # 형식 버전, 생성 시각, 파일별 바이트 수·SHA-256
  wodsiege.sqlite        # 독립 SQLite 스냅샷
  uploads/
    <video-id>
```

`verify`는 파일 목록·중복·안전한 상대 경로·SHA-256·크기·SQLite `integrity_check`·현재 aggregate 필드 형태·영상 참조를 확인한다. 예상 밖 루트 파일, 누락/추가 영상, SQLite WAL/journal 보조 파일이 있으면 실패한다. manifest와 파일을 함께 악의적으로 수정하는 공격에 대한 서명/진위 인증 기능은 아니다. 모든 비즈니스 규칙의 재계산이나 영상 디코딩 검증도 수행하지 않는다.

## 새 디렉터리로 복구와 수동 전환

```bash
# 백업 전체 검증 후 복구 예정 정보만 출력
node scripts/data-backup.mjs restore --source ./backups/2026-09-06-01 --target ./data-restored-2026-09-06-01

# 검증 성공 뒤 새 경로에 복구. 기존 ./data에는 쓰지 않는다.
node scripts/data-backup.mjs restore --source ./backups/2026-09-06-01 --target ./data-restored-2026-09-06-01 --execute --server-stopped
```

복구는 **대상을 만들기 전에 전체 백업 검증**을 완료하고, 복사한 파일의 체크섬을 다시 확인한다. 복구 DB의 `sessions`만 빈 객체로 바꾸고 무결성·상태·참조를 다시 검사한다. 계정과 비밀번호, 경기와 원장 등 나머지 JSON 데이터는 보존한다. 이전 로그인 토큰으로 접근할 수 없으므로 모든 사용자가 다시 로그인해야 한다. 이는 논리적 세션 무효화이며 디스크의 과거 바이트를 안전 삭제하는 기능은 아니다.

마지막에 `restore-receipt.json`을 작성하며 무효화한 세션 수와 최종 DB 해시를 기록한다. 이 영수증은 작업 당시 기록이며 서버 사용 후 DB의 최신 검증값이 아니다. 복구본은 백업 manifest 구조가 아니므로 `verify --source <복구본>`의 대상이 아니다.

명령이 종료 코드 0으로 끝났고 영수증이 있는지 확인한 뒤, 운영자가 서버의 `WODSIEGE_DATA_DIR`를 복구 경로로 변경하고 시작한다. 도구는 서비스 시작·설정 변경·현재 data 덮어쓰기·기존 데이터 삭제를 하지 않는다. 운영자 부트스트랩 환경 변수는 의도한 계정 생성이 아닌 경우 제거하고, `/api/health`, 기존 사용자 재로그인, 경기·원장·권한 있는 영상 열람을 확인한다. 복구본을 쓴 이후 원본으로 전환하면 그 사이의 변경이 사라질 수 있으므로 실제 요청을 받기 전 인수한다.

실패하면 생성된 새 대상은 조사용으로 남겨두며 자동 삭제하지 않는다. 종료 코드가 0이 아니거나 영수증이 없으면 활성화하지 않는다. 백업도 성공 종료와 별도 `verify` 성공을 모두 확인한다. 재시도는 새 대상 이름으로 수행한다. 디스크 고장/정전까지 보장하는 원자적 배포·재해복구 체계는 아니며, 중요한 백업은 독립 저장소에서 정기 복구 연습이 필요하다.

## 로컬 검증

```bash
node --test tests/backup.test.mjs
```

테스트는 임시 SQLite와 임시 영상만 사용한다. 기본 dry-run, 정지 확인 필수, 실제 round trip·세션 무효화·원장/경기 보존, 커밋된 WAL 반영, 파일 권한, 손상/체크섬/경로 탈출/링크/누락 영상/기존 대상 거부를 확인한다. 실제 운영 데이터에 대한 백업·복구는 수행하지 않았다.
