01 / Problem

Problem · 그냥 기록만 비교하면 안 될까?

A 체육관은 “우리가 5분 만에 끝냈어!”, B 체육관은 “우리는 4분 50초야!”라고 말합니다. 그런데 운동 횟수나 자세 기준이 다르면, 숫자가 빨라도 더 잘했다고 말하기 어렵습니다.

공통 규칙이 없다면

누가 이겼는지부터 다툴 수 있어요.

메신저로 약속하고 영상과 기록을 따로 보내면, 어느 규칙에 동의했는지 찾기 어렵습니다. 틀린 결과가 순위에 반영됐을 때 고친 이유도 남기기 어렵고요.

이 앱이 하려는 일

약속과 증거를 한 경기에 묶어요.

운동·선수·시간을 먼저 합의하고 잠급니다. 양측의 증거를 확인한 뒤 결과를 확정하며, 나중에 고치더라도 이전 결과와 변경 이유를 남깁니다.

Box = 크로스핏 체육관
배송 상자가 아니라, 회원들이 함께 운동하는 체육관과 그 공동체를 말합니다.
WOD = 정해 놓은 운동 과제
Workout of the Day의 줄임말입니다. 무슨 동작을 몇 번 하고 어떻게 점수를 낼지 정한 ‘운동 문제지’로 생각하면 됩니다.
Siege = 도장깨기 대결
도전하는 체육관이 지키는 체육관과 겨룹니다. 이겨도 체육관 소유권이나 지역 영토를 가져가는 것은 아닙니다.

02 / Solution

Solution · 지민과 민수의 한 경기를 따라가 봅시다.

가상의 ‘성수 Box’가 경기를 열고, ‘서울숲 Box’가 도전합니다. 각 체육관 대표 한 명이 출전하는 개인전입니다. 아래 이름·기록은 설명용 예시이며 실제 회원이나 경기 데이터가 아닙니다.

대표 선수 민수

  1. 계정을 만들고, 우리 체육관 소속이 됩니다.

    선수는 가입 후 체육관에 가입을 신청합니다. 체육관 관리자가 승인하면 주 소속이 정해집니다. 운영자는 앱 전체의 체육관 승인과 분쟁을 담당하는 별도 역할입니다.

  2. 대결에 참가할 수 있는 체육관인지 확인합니다.

    각 체육관의 서로 다른 승인 회원 3명이 위치 사용에 동의하고 현장 확인을 해야 합니다. 현재 규칙은 체육관 중심에서 150m 이내, 위치 오차 100m 이하, 측정 후 10분 이내입니다. 세 사람이 동시에 확인할 필요는 없습니다. 여기에 운영자의 체육관 승인도 있어야 대결에 참가할 수 있습니다.

    GPS는 휴대전화가 알려 주는 위치입니다. 한 사람이 여러 계정을 쓰거나 위치를 속이는 문제까지 해결한 것은 아닙니다.

  3. 같은 운동, 같은 조건으로 약속하고 잠급니다.

    성수 Box 관리자가 운동, 개인/팀, 일정, 장소 방식을 정합니다. 서울숲 Box의 도전을 수락한 뒤 양측 관리자가 출전 명단에 동의하면 조건과 명단이 잠깁니다. 한 장소에 모이거나 각자 체육관에서 진행할 수 있습니다. 시작 전에는 취소할 수 있지만, 시작 후에는 일방적으로 취소할 수 없습니다.

  4. 운동을 하고, 영상과 직접 작성한 기록을 제출합니다.

    예시 운동은 SIEGE 90: 스쿼트 15회와 버피 15회를 3라운드, 총 90회 수행하는 10분 제한 과제입니다. 정해진 양을 끝내는 데 걸린 시간을 겨루는 For Time 방식입니다. 예정 시각부터 경기를 시작하고 선수별 시간·유효 횟수·무효 횟수·메모·영상 시점을 입력합니다.

    실제 MP4/WebM 영상 파일을 올립니다. 현재는 체육관 한쪽당 증거 파일 하나, 최대 100MB입니다. AI가 자세나 점수를 자동으로 판독하지 않으며 앱 안에서 촬영하는 기능도 없습니다.

    운동 예시는 소프트웨어 채점 설명용입니다. 개인에게 적합한 운동 처방이나 안전성 확인을 대신하지 않으며, 템플릿은 코치의 운영 승인이 필요합니다.

  5. 양쪽 모두 제출한 뒤, 서로의 증거를 확인합니다.

    한쪽만 제출했을 때 상대의 기록과 영상은 숨겨집니다. 양쪽이 제출해야 상대 자료가 열리므로, 상대 숫자를 먼저 보고 자기 기록을 맞추기 어렵게 합니다. 운영자는 확인할 수 있습니다. 영상은 공개 홍보 영상이 아니라 권한 있는 경기 관계자가 보는 검증 자료입니다.

    예정 시각이 토요일 15시라면 제출 마감은 일요일 15시(+24시간), 검토·이의 마감은 월요일 15시(+48시간)입니다. “이 기록에 문제가 있어요”라고 이의를 제기하면 판정이 보류됩니다.

  6. 검토 기간이 끝난 뒤 확정하면, 점수가 반영됩니다.

    지민이 90회를 5분에, 민수가 90회를 5분 20초에 완료했고 양측이 인정했다고 해 봅시다. 검토 마감 후 체육관 관리자가 확정하면 성수 Box가 승리합니다. 시간이 지났다고 저절로 확정되는 것은 아닙니다. 이의나 미응답이 있으면 해당 경기와 독립적인 운영자가 근거를 남겨 처리합니다.

잠깐, 이럴 때는?

확정 버튼을 누르면 항상 점수가 오를까요?

아래는 실제 서버에 연결하지 않는 설명용 상황 카드입니다.

기다립니다. 먼저 동의해도 이의 제기 시간은 남겨 둡니다.

양쪽이 모두 제출하고 서로 확인했더라도 검토 마감 전에는 일반 확정을 할 수 없습니다. 이 기간에는 확인을 마친 쪽도 이의를 제기할 수 있습니다.

이미 확정한 경기인가? → 다시 점수를 주지 않음
증거가 빠졌거나, 이의가 있거나, 양측 검토가 끝나지 않았나? → 일반 확정 불가
아직 검토 마감 전인가? → 기다림
위 조건을 모두 통과하고 관리자가 확정을 요청했나? → 결과와 점수를 한 번 반영

운영 판정은 별도 절차입니다. 분쟁 상태이거나 검토 기한이 지나야 가능하며, 양측 증거 없이 정상 승자를 확정할 수는 없습니다. 증거 미제출은 자동 패배가 아니라 운영자가 무효 처리할 수 있는 사유입니다.

모든 상황을 글로 보기
  • 검토 기간 중: 양측 동의만으로 바로 확정하지 않습니다.
  • 양측 제출·검토 완료, 기간 종료: 관리자 요청으로 정상 확정합니다.
  • 이의 제기: 일반 확정을 멈추고 독립 운영자가 근거를 남깁니다.
  • 한쪽 증거 없음: 정상 승자를 낼 수 없습니다. 검토 기한 경과 후 운영자가 무효 처리할 수 있습니다.
  • 이미 확정됨: 같은 요청을 다시 보내도 점수와 보상이 중복되지 않습니다.

시간만 재는 대회인가요?

운동 방식도, 참가 부문도 나뉩니다.

AMRAP은 정해진 시간 동안 유효 동작을 많이 하는 방식입니다. Rx는 정해진 원형 과제, Scaled는 조정한 과제이며 서로 순위를 섞지 않습니다.

개인전은 한 명씩, 팀전은 세 명씩입니다. 현재 3인 Open은 성별·연령 세부 제한을 두지 않은 개발용 구성입니다. 세 명이 각자 같은 운동을 하고 결과를 합칩니다. 릴레이가 아닙니다.

끝내지 못했을 때도 기준이 있습니다.

For Time 개인전은 완료자가 미완료자보다 앞섭니다. 둘 다 완료하면 빠른 쪽, 둘 다 미완료면 유효 횟수가 많은 쪽이 앞섭니다.

팀 For Time은 ① 완료한 인원 수 → ② 미완료자들의 유효 횟수 합 → ③ 완료자들의 시간 합 순서로 비교합니다. AMRAP은 유효 횟수를 합칩니다. 비교값이 모두 같으면 무승부입니다.

무효 동작은 유효 횟수에 포함하지 않습니다. 별도로 적은 무효 횟수를 유효 횟수에서 또 빼지는 않습니다.

‘실력 점수’와 ‘쓸 수 있는 포인트’는 달라요.

Rating / 실력 비교

레이팅은 순위를 위한 점수

상대의 실력 점수를 고려하는 Elo 방식입니다. 같은 부문에서 양쪽 모두 1000점으로 시작한 첫 보상 대상 경기라면, 승자는 1012점, 패자는 988점이 됩니다. 항상 12점씩 움직이는 것은 아닙니다.

개인/팀과 Rx/Scaled별로 따로 계산합니다. 동네·구 선택은 볼 체육관만 거르는 기능이지 별도의 점수를 만드는 기능이 아닙니다. 반영 경기 3회 미만은 임시 등급입니다.

Points / 활동 보상

Box 포인트는 꾸미기에 쓰는 잔액

보상 대상 경기를 정상 완료하면 승패와 관계없이 양쪽 Box가 각각 20P를 받습니다. 30P로 프로필의 ‘챔피언 실드’ 장식 하나를 한 번 구매할 수 있습니다.

예를 들어 서로 다른 날의 보상 대상 경기 두 번으로 40P를 모아 실드를 사면 10P가 남습니다. 레이팅은 깎이지 않습니다. 현금 결제·환전·거래 기능이 아닙니다.

반복 경기로 점수를 무한히 얻지는 못합니다.

같은 두 Box의 경기는 서울 시간의 예정 경기일 기준 하루에 먼저 확정된 유효 경기 하나만 레이팅과 보상에 반영합니다. 부문을 바꿔도 같은 제한을 받습니다. 무승부도 유효 경기이며, 서로 레이팅이 다르면 무승부에서도 점수가 변할 수 있습니다.

나중에 결과가 잘못된 것으로 밝혀지면?

운영자가 이유를 남겨 정정합니다. 이전 결과를 이력에 보존하고, 그 뒤 경기들의 레이팅도 확정 순서대로 다시 계산합니다. 무효 경기의 보상은 회수하며, 하루 한 번 보상 대상이 다른 경기로 옮겨갈 수도 있습니다. 이미 포인트를 썼다면 잔액이 음수가 될 수 있고 추가 소비가 막힙니다. 이는 앱 안의 미정산 포인트이지 현금 청구가 아닙니다.

휴대전화 안에서 모든 일을 하나요?

아닙니다. 화면, 규칙을 처리하는 서버, 데이터를 보관하는 저장소가 일을 나눕니다. API는 앱이 서버에 “이 기록을 저장해 줘” 같은 요청을 보내는 약속된 통로입니다.

③ 기록과 영상 저장소

회원·경기·점수 이력은 데이터베이스에, 큰 영상 파일은 별도 폴더에 저장합니다.

개발자용 이름으로는 화면이 React/TypeScript, Android 포장이 Capacitor, 서버가 Node/Express, 데이터베이스가 SQLite입니다. 이 이름을 외울 필요는 없습니다.

현재 APK만 설치한다고 어디서나 사용할 수 있는 것은 아닙니다.

APK는 Android 설치 파일입니다. 지금은 USB로 연결한 개발 PC의 서버가 켜져 있어야 핵심 기능이 동작합니다. 휴대전화의 localhost:8787 요청을 PC로 이어 주는 개발용 연결을 사용합니다. 독립적인 온라인 서비스가 되려면 서버 배포와 HTTPS 보안 연결이 필요합니다.

앱은 조작 후 새 상태를 불러오고, 활성 화면에서는 30초마다 다시 조회합니다. 실시간 영상 중계는 아닙니다. 알림도 현재는 앱 안의 알림이며 휴대전화 잠금 화면에 뜨는 푸시 알림은 아직 없습니다.

03 / Schema changes

Schema changes · 앱은 무엇을 기억하나요?

스키마는 저장할 정보의 항목과 모양을 정한 설계도입니다. 학교 대회 기록부의 ‘참가자·반·종목·기록·확인자’ 같은 칸을 떠올리면 됩니다. 여기서는 처음 만든 앱의 저장 구조를 설명합니다. 이번 설명서 생성 작업은 앱 코드나 데이터베이스 구조·기존 데이터를 바꾸지 않습니다.

원본 기록: 무엇이 실제로 있었는가

회원과 소속, 합의한 경기 규칙, 제출한 기록과 영상 정보, 확인·이의·판정 이력이 기준입니다. 점수가 이상하면 이 기록을 따라 확인합니다.

계산 결과: 원본에서 무엇이 나오는가

레이팅, 반영 경기 수, 보상 반영 내역과 포인트 잔액을 저장해 사용합니다. 순위 번호와 동네별 목록은 화면에 보여 줄 때 계산합니다. 잘못된 경기를 정정하면 관련 점수 요약도 다시 맞춥니다.

아래는 개발 담당자도 확인할 수 있는 전체 저장 묶음 목록입니다. 영어 이름은 코드와 대응하기 위한 표기이므로 외우지 않아도 됩니다. JSON은 이름과 값을 묶어 적는 데이터 형식입니다.

경기 안에는 어떤 세부 정보가 들어 있나요?
  • 운동 복사본: ID·이름·버전·For Time/AMRAP·설명·동작 목록·제한 시간·기준 횟수·Rx/Scaled를 경기 안에 고정합니다. 나중에 템플릿을 바꿔도 이미 합의한 경기의 운동을 몰래 바꾸지 않습니다.
  • 일정과 출전: 예정 시각, 제출/검토 마감, 생성·수락·잠금·확정 시각, 체육관별 선수 ID 목록, 합의한 양측을 기록합니다. 잠글 때 선수 ID·이름·당시 Box를 복사해 소속 이전 후에도 그 경기의 출전 소속을 보존합니다.
  • 제출 한 묶음: Box별 영상 ID·제출 시각과 선수별 완료 여부·초 단위 시간·유효/무효 횟수·메모·영상의 확인 시점입니다. 제출 후 같은 내용의 재요청은 중복 처리하지 않지만, 다른 내용으로 덮어쓰지는 못합니다.
  • 검토와 결과: 확인한 Box 목록, 이의 사유·제기자·시각, 승리 Box 또는 무승부와 근거, 경기 상태를 저장합니다. 이력에는 사건 ID·행위자·시각·종류·세부 내용이 추가되고, 정정할 때 이전 상태/결과도 남습니다. 무승부와 경기 무효는 다른 상태입니다.
  • Box 세부 상태: 원시 현장 위치에는 회원별 위도·경도·오차·측정 시각이 들어갑니다. 서버의 active는 회원·현장 확인 조건이며 operatorVerified는 별도 운영 승인입니다. 실제 경기 자격에는 둘 다 필요합니다. 공개 응답에서는 원시 현장 좌표를 제외하고, 승인 근거도 권한에 따라 제한합니다.
휴대전화에도 저장하나요? 다른 사람에게 무엇이 보이나요?
  • 기기 쪽: localStorage(앱 화면의 지속 저장 공간)에 서버 주소 wodsiege-server와 경기 생성 초안 wodsiege-match-draft를 둡니다. 초안은 생성 성공 후 지우며 영상이나 비밀번호를 저장하는 기능이 아닙니다.
  • 로그인 증표: sessionStorage(화면 세션용 저장 공간)의 wodsiege-token을 요청에 붙입니다. 서버는 그 증표의 해시, 즉 원문 대신 계산한 검증값을 저장합니다. 비밀번호도 소금값과 scrypt 검증값으로 저장하며 응답에 보내지 않습니다. 앱을 완전히 종료하면 다시 로그인이 필요할 수 있습니다.
  • 로그아웃·주소 변경: 로그아웃은 서버 세션을 없애고 기기의 증표를 지웁니다. 서버 주소 변경은 기기 쪽 로그인 증표를 지우지만, 이전 서버의 계정·경기 데이터 자체를 삭제하지는 않습니다. 만료 세션은 새 로그인 증표를 발급할 때 정리합니다.
  • 보여 주는 범위: 서버가 사용자 권한에 맞춰 응답을 만듭니다. 경기 자료는 참가 권한과 제출 상태로 제한하고, 영상은 별도로 권한을 확인합니다. 체육관 주소·중심 위치와 사용자의 원시 현장 위치는 서로 다른 정보입니다.
개발자를 위한 저장 방식·통신 약속·변경 주의점
  • 신규 구조: 앱 구현에서 추가한 SQLite 파일은 data/wodsiege.sqlite입니다. SQL 구조는 state(id INTEGER PRIMARY KEY CHECK(id=1), data TEXT NOT NULL)이며, ID 1의 JSON에 위 묶음을 저장합니다. 테이블이 없다면 생성하고, 이미 있는 상태는 다시 시작해도 유지합니다.
  • 한 번에 저장: 하나의 요청이 바꾸는 상태는 트랜잭션이라는 묶음으로 저장합니다. 중간 실패 때 일부 점수만 저장하지 않게 합니다. WAL 저널과 보조 파일도 운영 저장물에 포함되므로 백업은 일관된 DB와 영상 파일을 함께 고려해야 합니다.
  • 큰 파일: 영상 본문은 data/uploads/에 영상 ID로 보관합니다. DB의 영상 설명표와 별개이므로 DB만 복사하면 영상을 복원할 수 없습니다. 보관/삭제 자동화와 장기 용량 관리는 아직 없습니다.
  • 통신 약속: /api 요청·응답은 주로 JSON이며 로그인 증표를 Bearer 인증 헤더로 전달합니다. 영상 업로드는 파일과 동의를 담는 multipart 형식, 영상 조회는 인증된 파일 응답입니다. 경기 시각은 UTC 기반 ISO 문자열로 주고받고 화면은 현지 시간으로 표시합니다. 하루 한 번 반영 기준은 서울 시간입니다.
  • 저장하지 않는 화면 결과: 순위 번호·임시 등급 표시·지역 필터 목록·운영 집계는 원본에서 계산합니다. 기한 알림은 저장 사건 알림 외에 조회 시 생성하는 것도 있습니다. 응답의 updatedAt은 응답 생성 시각이며 모든 항목이 그 시각에 변경됐다는 뜻은 아닙니다.
  • 정정과 일관성: 유효한 확정 경기들을 finalOrder 순서로 재계산하고 차이를 조정 장부에 추가합니다. 서버 저장은 한 트랜잭션으로 반영되지만 다른 사용자의 열린 화면은 다음 조회까지 이전 값을 보일 수 있습니다. 부하 상황에서의 반영 시간 보장은 아직 측정하지 않았습니다.
  • 정책 버전: 운동 템플릿은 경기별 복사본이 있지만 pilot-v1 정책 상수는 서버 코드에 있습니다. 이 정책 이름이나 운동 버전은 DB 마이그레이션 버전이 아닙니다. 향후 정책 변경 시 과거 경기 재계산에 미칠 영향을 검토해야 합니다.
  • 삭제·리셋·호환성: 이번 HTML 작성으로 추가/변경/삭제되는 앱 스키마나 의도적 데이터 손실은 없습니다. 기존 앱 데이터 초기화도 하지 않습니다. 현재는 새 클라이언트와 새 서버가 같은 약속을 사용하며, 체계적인 DB 버전 변환 기능은 없습니다. 향후 표 분리·필드 변경에는 백업, 데이터 이전 절차와 이전 앱 호환성 검증이 필요합니다.
  • 운영 전 기술 과제: JSON 통째 저장은 작은 시험 운영을 위한 선택입니다. 대규모 운영을 위해 표 분리·검색 인덱스·동시 접속·비동기 비밀번호 검증 등을 검토해야 합니다. 기존 검사에서 runtime 의존성 취약점은 0건이었지만 개발 도구의 @capacitor/cli → xcode → uuid 경로에 moderate 3건이 기록되어 있습니다. 이 결과를 보안 인증으로 해석해서는 안 되며 개발 도구 호환성을 고려해 후속 조치가 필요합니다.
